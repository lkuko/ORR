# 设计与实现约定

## 界面设计规格

- 场景：Operate。服务校园同学找闲置、管理交易和沟通交付；管理员可以核实并处理违规商品。
- 方向：校园物品目录，信息优先，实物图片与清楚的价格层级形成识别；不增加宣传式大横幅。
- 色彩：沿用现有 `#2854d9` 主色；纸白 `#ffffff`、底色 `#f5f7f6`、正文 `#203137`、次级 `#66738a`；价格使用 `#b7452b`。
- 字体：PingFang SC、Microsoft YaHei。保留已确定中文界面字体，不下载大字体文件。
- 布局：小程序 750rpx 流式，两列等宽商品卡（同类信息适合相同结构），32rpx 外边距、16rpx 列距；表单单列，底部操作区考虑安全区。管理台沿用现有侧栏与内容容器，扩展一致的列表、筛选和详情。
- 间距：8/16/24/32/48rpx；点击目标至少 88rpx。动作反馈 120–180ms，尊重减少动态效果；不用循环装饰动画。
- ColorUI：官方原生 WXSS 固定到明确 Git commit；仅在新组件/页面作用域引入基础组件，避免旧页面全局样式被覆盖；官方图标可全局导入。

## 后端与数据

继续使用 `campus-api` 的可信身份、事务、请求幂等、字段过滤。新增 `products`、`favorites`、`product_orders`、`product_messages`、`media_assets`、`media_checks` 六个集合；客户端数据库读写仍拒绝。

- products：卖家、标题、描述、分类、整数分金额、成色、公开交易区域、图片 ID、状态、可见性、收藏数、当前订单 ID、发布时间及排序键。
- favorites：`hash(userId, productId)` 固定 ID，active 标记；事务更新收藏记录与商品计数。
- product_orders：不可变商品/价格快照、买卖双方、状态、取消申请、时间。事务预订商品，拒绝本人购买和已预订商品。
- product_messages：仅订单双方查看，文本审核、幂等写入，结束后拒绝新留言。
- media_assets：上传者、文件 ID、微信审核 trace、绑定商品、创建时间。文件经服务端上传到不可由客户端覆写的私有存储。
- media_checks：平台审核回调结果，按 trace 固定 ID；独立回调函数拒绝客户端来源，核对 AppID、事件及版本。先到的回调也可以保存，避免与上传事务竞争丢失。

图片通过云函数上传压缩后的 JPG/PNG（每张最多 700KiB），避免客户端任意上传/覆盖已审核文件；6 张分别上传，单次请求上限独立校验。微信 `security.mediaCheckAsync` v2 异步检测。客户端可以刷新审核状态；未通过、超时、异常全部关闭发布。公开接口只为审核通过的商品图签发短期 URL。没有人工绕过自动安全审核的入口。

## 搜索与推荐

服务端按标题+描述的规范化字段作转义字面量查询，分类、状态与可见性共同过滤。分页采用排序键和最后一条记录游标；游标绑定当前筛选。每页 20，最多 40。

推荐分数 `72 × log2(1 + 收藏数) - 发布小时数`；存储等价键 `发布时间小时 + 72 × log2(1 + 收藏数)`，无需每小时全表重算。以 ID 解决同分顺序。推荐为动态排序，其他用户收藏可使跨页位置变化；前端按 ID 去重，刷新重新查询。不是机器学习或个性化推荐。

## 交易状态

新预约直接进入 `ACCEPTED`（待当面交付），保留旧 `PENDING` 订单的卖家确认和确认前取消分支。待交付订单仍需协商取消；买家在线下交接完成后确认交易完成。取消协商被拒绝进入 DISPUTED，管理员决定取消或恢复 ACCEPTED。取消后商品回到可出售（管理下架仍不可见），完成后为 SOLD。

封禁用户不能参与新的业务动作；交易状态推进再次读取双方账号。商品下架阻止新交易，不抹掉已有订单证据。管理员可以填写原因终止进行中的交易，覆盖争议裁定及商品下架、账号封禁后的收尾；只有争议订单允许恢复交易，且须重新核对双方账号和商品可见性。所有处置保留审计。

## 验证与运维

先建集合与索引、安全规则，再部署函数和页面；新增回调需在微信开发者工具消息推送绑定 `event/wxa_media_check`。资源写操作只面向已有测试环境，不删除既有资源。以真实审核回调作为安全链路验收条件。
