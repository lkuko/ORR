## 一、可放入简历的完整版本

### ORR 校园互助与内容治理平台｜微信小程序 + 云开发

**项目仓库：** [lkuko/ORR](https://github.com/lkuko/ORR)（私有仓库，展示前确认访问权限）

**技术栈：** JavaScript、WXML/WXSS、ColorUI、微信云开发 CloudBase、Node.js、NoSQL 文档数据库及事务、云存储、Vue 3、Vite、esbuild、Git。

**项目简介：** 面向单校区的跑腿、二手交易与文字社区平台，覆盖任务接单、商品搜索收藏、预约交付、留言、取消协商与内容治理，并提供独立管理后台。当前实现包含 16 个小程序页面、10 个业务模块及独立图片回调、16 个数据库集合。原跑腿/论坛完成测试环境双账号关闭调试验收；新增二手模块已完成真实图片审核链路、交易体验代码和云端归档冒烟，完整双账号验收仍按验收记录单独核对。

- **云开发架构重构：** 将独立服务端方案调整为“原生小程序 + 模块化业务云函数 + Vue 管理台”，统一云函数调用、身份校验与错误返回；按用户、任务、留言、论坛、举报、管理划分模块，通过 esbuild 生成独立部署产物。
- **订单状态与并发控制：** 设计接单、完成确认、取消协商和争议裁定状态机，在数据库事务中校验任务状态与操作角色，同步更新任务、参与者在途订单和事件记录；本地模拟 12 个身份并发接单仅一人成功，真实云端 12 路接单请求复测仅一次成功。
- **请求幂等与异常恢复：** 以“可信身份 + 请求编号”生成操作标识，并校验动作与参数摘要；将业务结果和幂等记录同事务提交，结合客户端待确认请求编号持久化，支持网络丢失响应后的重试，避免重复留言和重复状态变更。
- **权限与数据隐私：** 基于平台身份及云端管理员角色校验权限，关闭业务集合的客户端直接读写；通过服务端响应裁剪限制具体地点、取消原因和订单留言的访问范围，实现本人举报查询与处理结果回溯。
- **前端交互与内容治理：** 使用发送锁、请求序号和服务端返回结果更新页面，处理连续点击、异步响应乱序和发送失败草稿保留；完善举报回执、历史记录及管理员处置界面，适配长编号和窄屏布局。
- **商品检索与规则推荐：** 实现服务端关键词/分类查询、游标分页，以及收藏量与发布时间结合的可解释排序；使用用户/商品固定组合 ID 和事务维护收藏计数，预订商品与订单同时提交，防止重复收藏计数和一物多单。
- **图片安全与上传流程：** 接入 ColorUI 商品页面、分级图片压缩和私有云存储，采用异步审核资产/结果分表；按平台回调运行时来源、AppID 和事件版本校验身份，以 trace 固定 ID 幂等写入，未通过、异常或超时均阻止发布。已用测试环境真实送检验证通过结果落库，并确认客户端伪造回调被拒绝；新模块双账号交易验收仍待完成。
- **测试与部署验证：** 建立 76 项本地自动化测试，覆盖权限隔离、事务回滚、并发接单、重复请求、个人回收站期限与前端竞态；结合真实云环境归档恢复冒烟和既有双账号跨网络验收验证业务闭环，并通过资源 SHA-256 比对定位和修复管理台线上版本不同步问题。

| 方向 | 建议优先保留的三条 | 需要能现场解释 |

## 四、60–90 秒项目介绍

> 我的项目是 ORR 校园互助平台，覆盖校园跑腿、二手交易和文字社区，并提供独立管理后台。前端是微信原生小程序，业务运行在模块化 CloudBase 云函数，数据使用 NoSQL 文档数据库和云存储。
>
> 我重点梳理的是订单一致性和异常交互。例如两个请求同时接一单时，后端在事务中重新读取任务状态，只有符合条件的请求才能完成接单；如果留言已经写入，但响应在网络中丢失，客户端会保留请求编号，重试时由服务端返回原结果。
>
> 权限方面，具体地点和留言由服务端控制返回范围，管理员也必须通过云端角色检查。前端则处理了重复点击、旧请求覆盖新结果和失败后草稿丢失的问题。
>
> 本地有 76 项自动化测试。原跑腿和校园圈完成过两个真实账号关闭调试及跨网络验收；二手模块的真实图片审核和云端归档恢复链路已验证。本轮交易简化、回收站和评论响应改动通过本地自动测试，完整新模块多账号实机验收仍按验收记录区分。项目处于测试环境，没有声称正式上线或完成大规模压力测试。

这里的“我”应在确认自己能够说明设计、修改代码并复现实验后使用。若某部分主要由工具辅助完成，面试时可说明如何审查代码、设计验证和修复问题。
