## 一、项目介绍与架构选择

### Q01：请用一分钟介绍这个项目。

**答：** ORR 是面向单校区的跑腿、二手交易和文字社区平台，通过 Vue 管理台处理举报、用户和交易争议。原生小程序调用模块化 CloudBase 云函数，业务文档和图片分别持久保存在文档数据库与私有云存储。重点包括事务状态机、请求幂等、服务端权限裁剪、异步图片审核，以及统一订单与三类个人回收站。项目有历史自动化和双账号验收记录，近期记录管理改动尚未回归；它处于测试环境，没有正式上线或大规模容量结论。

### Q02：这个项目解决了什么问题，业务范围是什么？

**答：** 核心是把校园需求从发布、接单或预约延伸到完成、取消协商和争议处理。二手支持搜索、分类、收藏和规则推荐；文字社区提供交流，举报与管理台形成处置闭环。统一订单中心减少入口分散，独立回收站允许用户整理本人历史。当前单校区试用、线下结算，没有微信支付、钱包、物流、多校区、学生认证或实时聊天。

### Q03：为什么改用微信云开发？

**答：** 项目入口本来就是微信小程序，云开发提供平台身份、云函数、数据库及内容安全能力，减少维护独立 HTTP 服务和自建身份衔接的工作。重构后页面通过服务层调用 action，统一在云函数检查权限和业务规则。代价是依赖平台 SDK、事务限制、部署流程和计费模式；选型是针对当前规模作出的权衡，不意味着云开发在所有项目中都优于独立后端。

### Q04：你这算微服务吗？

**答：** 不算。campus-api 是一个模块化业务云函数，聚合用户、任务、留言、论坛、举报、管理以及商品、交易、媒体和二手管理路由；任务内部另拆归档模块。media-callback 是独立的可信图片审核事件入口。两个部署单元不等于一套微服务体系；代码职责划分、独立部署和跨服务一致性是不同问题，是否进一步拆分应由实际需求决定。

### Q05：为什么没有用 Redis、消息队列或分布式锁？

**答：** 当前接单约束可以依靠数据库事务和同一任务文档的竞争解决，写请求重试通过幂等记录处理，没有必要额外引入一个锁服务。消息队列更适合需要异步解耦的通知、批量处理等场景，但核心状态最终仍要正确提交。增加这些组件会增加故障模式与维护成本，应该在需求和测量结果支持时采用，而不是为了丰富技术栈。

### Q06：一次接单从前端到数据库经过哪些步骤？

**答：** 用户确认后，详情页调用 tasks 服务，云调用封装生成或复用请求编号；平台调用云函数，入口取得可信身份，处理器鉴权并查幂等记录。事务中再次读取操作人和任务，验证任务可接、操作者不是发布者，然后保存任务、参与者在途任务和事件，最后保存幂等结果并提交。前端拿到经过裁剪的服务端结果更新页面。

**源码定位：** [调用链讲解](technical-study-guide.md#t02)、[任务动作](../cloudfunctions/campus-api/modules/tasks.js)、[统一处理器](../cloudfunctions/campus-api/app.js)。

## 二、认证、授权与隐私

### Q07：怎么防止用户把请求里的 userId 改成别人？

**答：** 业务身份不从用户提供的 userId 推导。小程序入口读取平台 SDK 的微信身份并校验 AppID，再生成内部用户 ID；后续资源归属使用该身份。请求中的任务 ID 只是目标资源标识，仍要检查当前人是否有权操作。测试会提交伪造的 OpenID、角色和 uid，确认这些参数不会带来用户或管理员权限。

### Q08：认证和授权有什么区别？项目分别怎么做？

**答：** 认证证明“谁在调用”，小程序使用微信平台身份，网页后台使用 CloudBase 账号认证；授权判断“能操作什么”，包括用户是否启用、是否管理员、是否订单参与者、是否符合当前状态。认证成功不能代替资源授权。例如普通微信用户可以登录，但仍不能调用管理员接口，也不能读取陌生订单的留言。

### Q09：为什么对 OpenID 做哈希？哈希后就安全了吗？

**答：** 内部用户 ID 把身份来源、AppID 和 OpenID 一起做 SHA-256，便于建立稳定的内部关联，并减少接口直接返回原始 OpenID。实现还用了分隔符和来源命名空间。哈希不是加密，也不是登录凭据；泄露一个内部 ID 后，安全性仍应由权限检查保证，不能依赖 ID 难猜，更不能声称哈希后就完成了匿名化。

### Q10：所有数据库集合禁止客户端直接读写，为什么云函数还能操作？

**答：** 客户端访问与服务端访问属于不同权限边界。本项目让小程序和网页只调用云函数，服务端 SDK 负责访问数据库；云函数随后自行校验身份、角色和资源关系。规则文件写了拒绝访问还不够，要确认实际部署规则，再用客户端 SDK 尝试直接读写，验证确实拒绝。高权限服务端代码写错授权仍然可能泄露数据。

### Q11：具体地点只在接单后显示，是怎么实现的？

**答：** 在服务端返回值中实现。公开列表强制用公开视图，具体地点为 null；详情中只有发布者或成功接单者获得具体地点。前端根据返回标记展示，但不是由前端隐藏来保护。还要单独控制留言接口，不能只把任务详情页做权限判断，却让知道 taskId 的人绕过页面直接查询留言。

### Q12：管理员账号登录后是否就能调用所有管理操作？

**答：** 平台账号登录提供可信 uid，云函数仍要查 admin_users，要求启用且角色为 ADMIN，再验证动作的业务条件。跑腿争议裁定只处理对应争议状态；二手管理员可填写原因终止进行中的交易，但恢复仅限争议单，不能概括成所有管理动作都使用同一个状态条件。前端 token 布尔值只是界面状态，修改它不会改变云端权限。

**源码定位：** [身份与授权](technical-study-guide.md#t03)、[数据裁剪](technical-study-guide.md#t04)、[管理模块](../cloudfunctions/campus-api/modules/admin.js)。

## 三、订单状态机与事务

### Q13：两个人同时接一单，怎样保证只有一个成功？

**答：** 接单在事务中读取任务并检查 OPEN、可见、未过期等条件，随后写入接单者并改为 ASSIGNED。竞争请求会修改同一个任务文档；冲突的一方重试时重新读状态，如果已经被接走就返回 TASK_NOT_OPEN。关键是“事务内读和校验”，不是在事务外检查一次后直接覆盖，也不是只靠前端按钮防重复。

### Q14：为什么只用“先查任务是否 OPEN，再 update”不够？

**答：** 检查与更新之间存在时间窗口。两个调用可能都读到 OPEN，随后分别写自己的接单身份。如果读取和写入不在正确的一致性边界内，后一写可能覆盖前一写。事务把状态读取、条件判断和关联写入放到一次可检测冲突的提交尝试中；失败后必须重做读取和业务判断。

### Q15：你的事务具体包含哪些写入？

**答：** 接单事务不仅写任务，还通过 saveTask 更新参与者的 activeTaskIds 和用户修订号，写入任务事件，再由统一处理器写入幂等结果。这样不会出现任务已接但事件没记、任务已结束但在途索引没清理的部分结果。内容安全检查在事务外执行；页面一次点击发出的多个独立云调用，也不天然属于同一个事务。

### Q16：事务、锁、状态机和幂等分别解决什么问题？

**答：** 状态机规定哪些操作合法；事务保证本次关联读写的提交边界并处理竞争；锁是一种并发协调手段，项目没有额外实现分布式锁；幂等让同一个写操作重试时复用原结果。不同人用不同请求编号争抢同一单，主要靠事务和状态机；同一个人因网络异常重发同一操作，主要靠幂等。它们互相配合，但不能互相替代。

### Q17：为什么取消争议要保存 cancelResumeStatus？

**答：** 取消申请可能发起于 ASSIGNED，也可能发起于 COMPLETION_PENDING。如果管理员裁定继续履行，应该恢复申请前的状态；一律恢复成 ASSIGNED 会丢失“接单者已提交完成”的信息。因此申请时保存原状态，恢复时检查它是否合法，并检查双方账号是否有效，避免恢复一条仍有被封禁参与者的订单。

### Q18：管理员封禁用户时，用户刚好在接单，怎么处理？

**答：** 写事务中重新读取操作人状态并触碰用户文档，任务变更也更新相关用户的在途任务集合。封禁操作修改同一用户文档，竞争会由事务处理；重试时重新检查有效性。封禁还根据 activeTaskIds 处理关联任务。这个设计解决当前业务的竞争窗口，但会增加用户文档热点，不能直接扩展到无限在途任务。

### Q19：为什么发送留言还要更新任务上的 messageRevision？

**答：** 留言发送要和订单关闭产生正确竞争。如果只读取任务状态，然后只写一条新留言，它与关闭任务可能写不同文档。发送时更新同一个任务的 messageRevision，让它与完成、取消或处置任务的写操作竞争，重试时重新判断订单是否已结束。这个字段用于共同文档写入，不是留言序号，也不是前端实时消息机制。

### Q20：发生事务冲突后为什么不能无限重试？

**答：** 无限重试会放大数据库压力和延迟，也可能超过函数执行时间。当前最多 7 次尝试，使用有上限的指数退避和随机抖动；只有识别出的事务冲突会重试，业务错误立即结束，耗尽后返回 BUSY。调用方可以提示稍后重试，并保留未确认编号。退避减少同步竞争，但不是限流或容量保证。

**源码定位：** [状态机](technical-study-guide.md#t05)、[事务](technical-study-guide.md#t06)、[退避](technical-study-guide.md#t08)、[跨操作竞争](technical-study-guide.md#t09)。

## 四、幂等与失败恢复

### Q21：按钮已经禁用，为什么还需要后端幂等？

**答：** 禁用按钮只减少当前页面的重复操作，无法覆盖网络重试、页面重启、脚本调用或服务端成功后响应丢失。例如留言已经写入，但手机收到超时，用户重新发送时仍可能产生第二条。后端幂等使用同一个业务操作编号识别重试，并返回第一次的成功结果。界面锁改善体验，服务端负责业务一致性。

### Q22：requestId 为什么还要和用户身份一起生成 operationId？

**答：** requestId 来自客户端，不能假设全局唯一，更不能允许一个用户通过猜到另一个人的编号取得其结果。操作标识加入可信 actorId 和用户/管理员命名空间，使编号在主体范围内解释。即使两个用户碰巧使用相同 requestId，也不是同一个操作。身份仍由服务端得出，不能由请求参数随意指定。

### Q23：相同 requestId 携带不同参数时怎么办？

**答：** 服务端还保存 action 与规范化参数的摘要。如果编号相同但摘要不同，返回 IDEMPOTENCY_CONFLICT，不能把新参数静默当作旧操作，也不能覆盖原结果。canonical 会对对象键排序，减少 JSON 对象键顺序差异造成的误判，但数组顺序仍然有意义。这里的摘要校验不是授权，授权已经在更前面完成。

### Q24：为什么幂等记录要在事务外、事务内各查一次？

**答：** 事务外读取让已完成的重试快速返回，也避免重复做内容检查；但两个首次请求可能都在事务外读到不存在，所以不能仅靠这一次检查。事务内再次读取，并把业务写入和幂等记录一起提交，才能处理竞争。事务外检查是优化，事务内检查与原子提交才是关键一致性环节。

### Q25：如果服务器提交成功后崩溃，客户端怎么知道结果？

**答：** 客户端不必靠超时判断提交是否发生，而是保留该操作的 requestId 后重试。如果事务已经成功提交，幂等记录和业务结果应同时存在，服务端返回原结果；如果未提交，重试可重新执行。本地测试模拟“服务端成功但客户端丢失响应”，重建客户端并复用存储后，确认仍只有一条留言。

### Q26：哪些失败需要保留待确认请求编号？

**答：** 网络错误、内部未知错误和 BUSY 具有结果不确定或适合重试的特征，当前会保留编号；成功或明确业务拒绝后清理。清理时机影响语义：结果未知就换新编号，可能重复提交；明确参数错误却一直复用旧编号，用户修改输入后也会混淆。代码按错误类别处理，而不是遇到任何 catch 都清空。

### Q27：幂等是不是相同内容永远只允许提交一次？

**答：** 不是。幂等作用于同一个逻辑操作编号；成功后再发送相同文字，使用新编号可以是一条新留言。业务去重则可能规定某个用户只能报名一次、某个自然键只能对应一个实体，是另一类约束。本项目没有宣称实现所有业务内容的全局去重，也没有把短时间内文本相同作为永久唯一条件。

### Q28：你能保证 exactly-once 吗？

**答：** 我会谨慎表述为“对相同操作编号，实现事务内一次提交效果及结果重放”。网络请求可以到达多次，外部内容检查也可能执行多次，客户端可能丢失存储。保证还有身份范围、记录保存期和调用方复用编号等前提。当前没有幂等 TTL，后续设计清理策略时还必须明确允许重试多久，不能笼统声称系统端到端 exactly-once。

### Q29：客户端 fingerprint 和服务端 SHA-256 摘要有什么区别？

**答：** 小程序 fingerprint 是对 JSON 文本计算的轻量指纹，用来定位本地未确认请求编号；服务端使用 canonical 加 SHA-256 判断 action 和参数是否一致。客户端指纹不是安全哈希、加密或可信授权依据。后台当前还把 JSON 文本作为 sessionStorage 指纹，可能含操作说明，应在后续优化为更少的本地载荷存储。

**源码定位：** [幂等原理与边界](technical-study-guide.md#t07)、[客户端封装](../miniprogram/services/cloud.js)、[服务端摘要](../cloudfunctions/campus-api/lib/validation.js)。

## 五、前端交互与异步状态

### Q30：多个页面同时登录时为什么不会重复发很多请求？

**答：** ensureLogin 会先看已有用户缓存，再看是否有正在执行的 loginPromise。已有 Promise 时直接复用，让多个调用等待同一个登录结果；完成或失败后在 finally 清空 Promise。用户缓存提高页面启动效率，不能替代云端用户状态检查。失败后清空进行中的 Promise，也让下一次重试不会永远拿到同一个已失败 Promise。

### Q31：为什么发送锁使用实例字段，不只看按钮的 loading？

**答：** loading 是展示效果，不该成为业务互斥的唯一来源。详情页在开始异步请求前同步设置 this.sendingMessage，后续事件立即看到锁并复用 sendPromise；同时用 setData 更新界面。成功后清草稿并追加服务端结果，finally 释放锁。后端仍要有幂等，因为这个锁只保护当前页面实例。

### Q32：发送失败后为什么草稿不会丢失？

**答：** 输入清空放在成功分支，失败分支只提示错误，因此当前页面保留原内容。发送期间输入修改也受限制，避免旧请求成功后清掉用户新输入。成功时按服务端 ID 去重再追加，并不是先制造一个假的成功对象。当前没有实现离开页面后恢复所有草稿，不应把“页面内失败保留”说成“永久草稿保存”。

### Q33：用户快速切换分类，旧请求后回来怎么办？

**答：** 发起每次加载时递增序号，并把当次序号保存在闭包中。响应回来只有序号等于最新值才允许更新列表、错误和加载状态。这样 A 类请求比 B 类慢，也不会把 B 的新页面覆盖。序号隔离只是忽略过时结果，不等于取消网络调用，也不会自动减少服务器已经消耗的资源。

### Q34：新留言已追加，为什么仍可能被旧列表覆盖？

**答：** 发送前可能已经有一个列表读取在路上，它读取的快照不含新留言。新留言成功并追加后，这个旧读取返回，如果直接替换列表就会让新留言消失。项目在开始发送时递增 messagesRequestId，使发送前发起的读取失效；同时成功后直接使用服务端消息结果更新当前列表。这是“读响应与写成功结果”的竞争，不只是两次列表加载的竞争。

### Q35：这些请求序号和后端 requestId 能合并吗？

**答：** 不建议。页面序号是短期、单页面的“最新请求”标记，目标是决定谁能更新 UI；幂等 requestId 是一个业务写操作跨重试使用的标记，需要在结果不确定时保持不变。前者每次读取通常递增，后者重试时恰恰不应该变化。混合使用会让 UI 过期处理和业务去重语义相互干扰。

### Q36：Vue 后台用了哪些响应式能力？

**答：** 用 ref 管理登录、筛选、列表和弹窗状态，用 computed 派生当前导航与审计排序。打开刚渲染的弹窗前 await nextTick，让 DOM 更新到可操作状态。项目没有引入 Pinia 或 Vue Router，简单导航由组件状态控制。编号组件封装缩略显示、完整复制和失败回退；长编号布局依赖换行及容器约束，不能只缩小字号。

**源码定位：** [登录](technical-study-guide.md#t12)、[发送锁](technical-study-guide.md#t13)、[竞态](technical-study-guide.md#t14)、[Vue 后台](technical-study-guide.md#t15)。

## 六、举报、内容安全与数据建模

### Q37：为什么内容检查放在事务外？

**答：** 它是外部调用，耗时和可用性不受数据库事务控制。把它放在事务内会拉长持有时间，冲突重试还可能反复调用。项目先规范化并检查文本，再在事务内重读身份与业务状态后落库。内容检查通过不代表业务状态永远有效；反过来，事务内落库成功也不能替代前面的内容安全判断。

### Q38：内容安全接口超时或返回 review 怎么办？

**答：** 当前只接受成功响应且 suggest 明确为 pass，其他结果不直接发布。接口异常返回 CONTENT_CHECK_UNAVAILABLE，未通过则返回 CONTENT_REJECTED。这样做可避免在未知状态下先展示公开内容，但会牺牲部分可用性。项目没有实现人工待审核队列，因此不能说 review 会自动进入一套人工审核流程。

### Q39：评论被删除或下架后，举报记录如何继续显示？

**答：** 创建举报时保存当时可见公开内容的短摘要，历史记录另有原因、处理状态、说明和时间；旧记录缺摘要时展示类型和缩略编号，不重新暴露隐藏正文。本人可把举报移入回收站或彻底清理，但只改 reporter 个人可见性字段，待处理举报仍留在管理队列。公开内容、本人记录和管理证据各有独立语义。

### Q40：“下架并处理举报”是一个事务吗？

**答：** 当前不是整个按钮动作共用一个事务。前端先调用 admin.hide，再调用 admin.resolveReport；每个动作各自在事务内保存业务和审计。如果第二步失败，可能已经下架但举报仍待处理，应提示并重试结案。后续可以设计一个组合动作，把确实需要共同提交的写入放进一个服务端事务，或显式记录可恢复的处理步骤。

### Q41：审计日志和普通运行日志有什么区别？

**答：** 审计日志记录谁对什么对象做了什么管理动作，以及原因、时间和结果，供业务追溯；运行日志主要记录 action、错误码和耗时，供诊断。当前单个管理员写动作与审计在同一事务提交，避免动作成功却没有记录。但普通数据库记录并不是防篡改审计存储，不能宣称数据库管理员也绝对无法修改它。

### Q42：为什么有一个 activeTaskIds 数组，不直接查询用户所有订单？

**答：** 它由任务状态变更同步维护，便于封禁事务按已知文档 ID 处理在途任务，避免在事务中执行当前适配器不使用的 where 查询。代价是多处状态变更都要维护一致性，用户文档可能成为热点，数组和封禁事务也可能增长。当前适合小规模试用，规模扩展时需要重新设计批量处理和封禁屏障。

### Q43：举报历史为什么需要 reporterId 和 createdAt 的复合索引？

**答：** 举报普通列表与回收站不只按 reporterId 查询，还区分 reporterArchived，并在回收站按服务端时间过滤 reporterArchiveExpiresAt，再按 createdAt 倒序。索引应对应这些查询路径，而不是每个字段随意单独建索引。本地声明不等于云端生效；历史有新增索引回读记录。本人界面仍显示最近 100 条，批量整理通过固定时间上界循环查询覆盖更早记录，这不等于界面已经有完整分页。

### Q44：金额为什么存整数分？昵称为什么存快照？

**答：** 金额先按十进制字符串解析为整数分，减少用二进制浮点直接做金额计算带来的问题；展示再转成两位小数文本。昵称作为提交时快照减少展示时的关联查询，也保留当时的显示名称，但用户改名后历史内容不会自动改。两者都是明确的数据表示选择；金额字段不意味着项目已经实现支付，昵称也不能用于判断资源归属。

**源码定位：** [内容治理](technical-study-guide.md#t10)、[数据与索引](technical-study-guide.md#t11)、[管理动作](../cloudfunctions/campus-api/modules/admin.js)。

## 七、测试证据与问题排查

### Q45：项目测试主要测什么，覆盖率是多少？

**答：** 已有用例覆盖校验、SDK 冲突分类、事务重试与回滚、权限、幂等、页面竞态，以及收藏、预约、图片来源、分页和二手归档等。记录中的 76 项通过属于历史版本 c4bc01e；最新共享页面、跑腿/举报回收站和批量操作没有运行回归，因此不能回答当前 76/76。没有公布覆盖率，测试数量也不能推出 100% 覆盖。后续应核对旧页面夹具并补充批量部分失败、权限及期限边界。

### Q46：本地模拟事务和真实云数据库有什么区别？

**答：** 内存 store 用快照和全局 revision 模拟乐观冲突，并主动禁止事务内列表查询，帮助测试业务代码。真实数据库的冲突粒度、超时、错误形状、网络故障和 SDK 行为不同，因此本地通过后仍需云端冒烟。尤其不能把模拟 store 的全局串行化效果或执行速度当作 CloudBase 的实现与性能。

### Q47：简历里的 12 路并发到底怎样测的？

**答：** 要分两种证据：本地业务测试创建 12 个模拟身份同时争抢同一任务；真实云端测试由 B 发布任务，A 一个真实账号同时发 12 个不同 requestId 的接单请求，结果一次成功、其余为任务不可接。真实测试不是 12 个真实账号竞争，也不是 12 QPS 或千级并发容量指标。它主要验证竞争下业务结果正确。

### Q48：为什么要求两台手机关闭调试并切换网络？

**答：** 这是为了验证实际账号、权限、网络和版本条件下的行为，避免仅凭开发工具环境认定通过。两个角色分别操作，可以核对地点可见性、留言、完成和取消流程；切换移动网络后重入验证读取和身份链路。它证明指定场景通过，不是所有机型、弱网情况、正式版或未来改动都已验证。

### Q49：用户说“操作成功”，为什么还要看云端记录？

**答：** 要把页面结果、操作编号和云端对象对应起来。二手三轮验收中，用户反馈手机已取消收藏，但云端仍是已收藏、计数 1，缺少手机取消回执；之后同账号在开发者工具点击取消，页面和云端才变成未收藏。后一步证明该链路有效，不能补记前一次手机操作或排序回落通过，也不能把未定位原因编成缓存问题。

### Q50：你遇到过最具体的并发问题是什么？

**答：** 云端并发验收中有一次竞争失败返回了 INTERNAL_ERROR，而不是可理解的业务结果。检查实际 SDK 错误发现是 ResourceUnavailable.TransactionConflict，原分类未覆盖。修复时让事务开始和提交阶段冲突都进入有限重试，并增加分类测试；重新读取后，任务已被接走的请求应返回 TASK_NOT_OPEN，持续冲突才返回 BUSY。

**源码定位：** [测试策略](technical-study-guide.md#t16)、[冲突分类](../cloudfunctions/campus-api/lib/store.js)、[分轮验收证据](acceptance.md)。

## 八、配置、部署与性能

### Q51：云函数为什么要用 esbuild 打包？

**答：** 项目曾出现部署后找不到相对模块的错误，因此将业务源码合并成单一入口，同时把 SDK 留为外部依赖并随部署目录携带依赖清单。模块化开发和单文件业务产物不矛盾。打包解决的是交付完整性，不能把构建成功直接等同于云端启动成功，仍应回读部署状态并调用实际函数验证。

### Q52：为什么 GitHub 已合并，线上管理台还是旧的？

**答：** GitHub 保存源码，线上静态托管保存上一次发布的构建文件，仓库没有自动部署工作流。当前的处理办法是重新构建并限定发布到管理台目录，再比较线上 HTML 引用的 JS/CSS 与本地文件哈希。项目曾检查到入口不一致和新资源 404，说明首先是发布未同步，而不是直接判断浏览器缓存有问题。

### Q53：把 env ID 放在 .env.local 里是不是就隐藏了？

**答：** 对 Git 源码来说可以避免误提交，但前端要使用的环境标识最终仍会出现在运行配置或构建代码中。Vite 的 VITE_* 变量就是客户端可用配置，不能放真正密钥。项目按要求把仓库实际 AppID、env ID 和域名改成占位符，本地文件被忽略；权限安全仍依赖平台认证、数据库规则和服务端授权，而不是隐藏环境标识。

### Q54：为什么加 .gitignore 后旧文件还会在 GitHub？

**答：** ignore 主要控制未跟踪文件，已进入索引的文件需要停止跟踪并提交删除；旧提交仍保存历史版本。项目中的 .agents 已移出跟踪但保留本机工具，配置模板使用占位符。然而没有重写历史，旧标识和旧截图仍可能从历史找到。若真密钥泄露，优先吊销或轮换；仅修改当前文件不能使旧密钥失效。

### Q55：你如何区分云函数慢、数据库慢和网络慢？

**答：** 记录客户端总调用时间、处理器内 serverMs、部分数据库操作耗时和内容检查耗时，再比较不同请求与冷/热实例样本。必须知道计时边界：serverMs 不包含所有平台启动和网络过程，databaseMs 不完全覆盖事务开始、提交和退避，coldStart 只是处理器首次调用标记。当前指标用于定位方向，还不是完整分布式链路追踪。

### Q56：项目有什么性能提升数据或 QPS 指标？

**答：** 有一个范围明确的历史对照：同一订单含两条留言，关闭调试的开发者工具在热实例下交替测 5 轮，分两次读取的总耗时中位数为 1,004 ms，合并读取为 519 ms，约下降 48%。另有一次评论提交总耗时 1,858 ms，收到回执后 13 ms 完成页面更新。这些不是手机普遍性能、评论平均提速或 P95/QPS 结论；持续压力测试和足够样本仍未完成。

**源码定位：** [部署与配置](technical-study-guide.md#t17)、[计时边界](technical-study-guide.md#t18)、[发布比对脚本](../scripts/check-admin-hosting.cjs)。

## 九、改进、扩展与个人贡献

### Q57：用户量增大后，你最先改什么？

**答：** 先测瓶颈。二手已有游标分页，不能再说所有列表都无分页；跑腿和校园圈仍有有限列表，举报界面只显示最近 100 条，二手批量整理还会先收集全部 ID。其他候选点有管理台举报对象 1+N 调用、用户文档热点、在途 ID 增长及幂等记录累积。再按数据量和监控选择分页、批处理作业、摘要接口或生命周期治理，不先为简历堆组件。

### Q58：你认为当前项目有哪些需要进一步审查的边界？

**答：** 近期优先复核统一页面与批量整理的角色、状态、到期和部分失败规则，并检查三类旧记录兼容；手机取消收藏与排序回落还留有证据差异。长期还要审视历史幂等结果在下架、清理之后的重放可见性、后台 sessionStorage 载荷、限流与正式环境。批量清理目前没有持久作业状态，不能宣称支持无限历史和任意中断恢复。这些是待验证或待改进范围，不是已经确认的全部漏洞。

### Q59：以后要支持支付、实时聊天或多校区，能直接加字段吗？

**答：** 不能只当页面扩展。支付需要独立交易状态、回调验证、幂等、退款和对账；实时聊天涉及连接、消息顺序、离线补偿和访问控制；多校区需要在身份、任务、查询、索引和管理权限中贯穿租户/校区边界。这些当前都未实现。应先明确业务不变量，再设计数据、接口和测试，不能沿用现有展示字段冒充新能力。

### Q60：如果项目使用了 AI 辅助，你如何说明自己的贡献？

**答：** 如实说明辅助范围，并聚焦自己能证明的工作：需求取舍、架构判断、代码审查、问题复现、测试设计和验收核对。可以现场展示一个问题从现象、定位、修改到验证的过程，例如响应丢失后的幂等重试或旧请求覆盖新留言。不能把无法解释的生成代码说成完全独立设计；对不熟悉的部分先补学，简历只保留能够负责和复现的内容。

**源码定位：** [已知限制与改进](technical-study-guide.md#t18)、[产品边界](product.md)、[简历证据表](resume-project.md)。

## 十、二手交易、图片与推荐（Q61–Q73）

### Q61：NoSQL 是不是没有数据库？数据如何持续保存？

**答：** 有数据库。这里用 CloudBase 文档数据库保存 JSON 形态的业务文档，并使用云存储保存图片。NoSQL 表示不是通过关系表和 SQL 作为当前访问模型，不表示没有持久化。云函数实例退出后数据仍在云端；本地 MemoryStore 只是测试替身。

### Q62：为什么图片上传成功后还不能发布？

**答：** 上传成功只表示图片字节已写入云存储，审核是另一条异步流程。只有可信审核结果为 PASSED、全部图片属于发布者且未被其他商品绑定，商品创建校验才通过。未审核、review、risky、超时和接口异常都不能视为通过。客户端隐藏发布按钮只是提示，实际约束仍在后端。

### Q63：为什么要两个云函数？

**答：** campus-api 面向经身份校验的业务调用，media-callback 面向微信平台事件。两者入口和信任来源不同，所以回调单独部署；不是为了堆微服务数量。两者共享文档数据库，业务写操作仍尽量保持一个事务。

### Q64：怎么处理回调重复、乱序或提前到达？

**答：** 回调结果按 trace 哈希独立落库，不依赖资产已经提交。首次结果生效，重复结果无操作；后续矛盾结果不能升级为通过。上传事务保存 trace 后可关联早到结果。未知 trace 最终没有资产引用，也不能直接让某个商品发布。

### Q65：如何证明收藏不会重复增加？

**答：** 用户/商品组合固定 ID 防止多条逻辑收藏，事务检查 active 是否真正改变，再增减商品计数和推荐键；请求级幂等负责重复网络请求。测试要同时覆盖同请求重试与不同请求编号的并发，而不只验证单击按钮。

### Q66：你的推荐为什么不需要定时刷新分数？

**答：** 展开公式后，当前时间对所有商品是同一常数，不改变排序，所以排序键只存发布时间小时与收藏对数分。收藏变更时重算即可。它是规则排序，不是针对每个用户训练的个性化模型。

### Q67：游标分页是不是绝对不会漏数据？

**答：** 不是。时间/ID 键和筛选绑定改善稳定性，创建时间上界阻止新记录挤进本次翻页；但热度和可见性会变化，已有商品可能跨页移动。前端去重解决重复显示，刷新解决重新发现；需要严格快照就要另行设计版本或快照集合。

### Q68：为什么图片设私有，但列表仍能显示？

**答：** 列表只请求商品 ID，云函数检查可见性和图片审核后签发短期 URL。客户端不能提交任意对象路径要求签名。私有存储不等于签出的链接不可分享；已发出链接可能在有效期内继续访问，下架只停止后续签发。

### Q69：怎样防止两人同时购买同一件商品？

**答：** 在事务中检查商品 AVAILABLE 和 activeOrderId 为空，写商品预订与订单。并发事务竞争同一商品，失败方重读后看到 RESERVED 而被拒绝。小程序的同步锁减少连点，但数据库事务才约束多个客户端。

### Q70：部署显示 Active 为什么还可能不能上传图片？

**答：** Active 只代表平台报告函数处于可用部署状态，不证明每条业务路径执行正确。存储、微信云调用权限、送检 API、消息推送、回调来源和数据库规则是不同环节。历史曾出现 -604101，之后通过开发者工具同步 config.json 权限；真实回调 SOURCE 为 wx_callback。需要以真实送检、回调落库和状态查询证明审核闭环，不能用部署成功代替。

### Q71：为什么“删除记录”没有直接删除订单文档？

**答：** 订单是双方共享的交易凭证。当前跑腿和二手只允许对已完成或已取消订单做个人归档，服务端按参与者身份选择 owner/helper 或 buyer/seller 字段；另一方和管理员继续读取共享订单与留言。举报也只改 reporter 字段。回收站清理是取消本人的可见性和恢复资格，不能称为物理删除、撤销举报或清除全部审计证据。

### Q72：回收站过期怎样避免记录又出现在普通列表？

**答：** 普通列表一直排除本人的归档标记，回收站额外检查服务端到期时间。到期只停止展示和恢复，不自动清除归档标记。恢复动作必须在到期前走事务并只清除本人的字段；重试归档不会延长保留期。

### Q73：评论响应慢，为什么不直接取消内容审核？

**答：** 审核是发布条件，不能靠绕过它换速度。项目把已审核并保存的评论回执直接追加到页面，减少成功后的整帖重读，并用请求序号隔离旧列表；订单详情把订单与首批留言合并为一次请求。优化应先明确耗时在哪一层，详情对照和单次评论计时不能混用，更不能把当前未回归改动说成已改善所有手机延迟。

## 十一、统一订单、回收站与批量操作（Q74–Q90）

### Q74：为什么把二手预约改成直接待交付，旧订单怎么办？

**答：** 原来预约后还需卖家确认，增加一次寻找入口与等待。新建订单在预约事务内直接设为 ACCEPTED，同时把商品设为 RESERVED，再由买家当面验货后确认完成。旧 PENDING 仍保留卖家确认和直接取消分支，避免历史数据失去处理入口。取消表现异常时先核对同一订单的状态与版本，不能只按按钮名字判断。流程简化没有取消后端权限和状态校验。

### Q75：统一订单中心为什么按“类型 → 身份 → 状态”组织？

**答：** 用户先判断自己要找二手还是跑腿，再判断自己是买家/卖家或发布者/接单者，最后找进行中或已结束记录，语义比“我的订单”和“跑腿订单”并列更清楚。回收站从“我的”独立进入，包含二手、跑腿、举报。这里只共享查询和操作的交互组织，三个业务对象仍由各自接口执行权限校验。

### Q76：为什么不在订单上只放一个 deleted 字段？

**答：** 单个 deleted 会把共享业务实体和个人视图混在一起，买家删除后可能连卖家历史也消失。当前按 buyer/seller 或 owner/helper 保存独立归档字段，举报使用 reporter。服务端从可信身份与归属关系推导可改字段，不能相信请求传来的角色。同一文档并发更新仍需事务重读，不是字段分开后就没有写冲突。

### Q77：7 天或 30 天保留期如何防止客户端绕过？

**答：** 只接受 days 为 7 或 30，服务端根据事务执行时 ctx.now 计算截止时间；查询和恢复都用服务端时间判断。客户端显示期限，不提供最终授权时间。归档标记保留，所以到期不会重回普通列表；重复归档不延长期限。已经清理或过期的正常详情读取和恢复路径会拒绝本人访问，历史幂等回执可见性则需另行审视。

### Q78：“删除记录”“清理回收站”“取消订单”有什么区别？

**答：** 删除记录是把本人的已结束订单或举报移入回收站；清理回收站使本人不可恢复，但保留共享凭证；取消订单改变履约状态，进行中的新二手交易需要对方同意或管理员处理。删举报不撤销举报，也不改变 OPEN/RESOLVED 等处理状态。当前没有定时物理销毁文档，因此也不能说回收站清理会释放全部数据库或图片空间。

### Q79：跑腿归档为什么直接 store.put，不复用 saveTask？

**答：** saveTask 会更新业务时间、维护 activeTaskIds 并写任务事件，而个人整理不应被记成一次履约状态变化。归档只修改本人字段，直接使用当前事务 store 保存。它仍经 app.js 的统一写事务、身份重验、操作人修订号和幂等提交；直接 put 不表示绕过事务。复用函数前要看其副作用是否符合当前语义。

### Q80：旧订单没有归档字段，为什么还能显示？

**答：** 普通查询采用本人 Archived 的 `$ne: true`，兼容缺字段的旧文档；回收站要求 Archived 为 true 且期限有效。若只写 Archived 等于 false，缺字段记录可能被排除。新增字段的读取默认值、查询条件和写入路径要一起考虑，不一定要先给所有历史文档批量补 false。

### Q81：“全部删除”怎样包括没有加载到页面上的记录？

**答：** 不只读取页面数组。跑腿与举报先获取服务端 snapshotAt，然后固定 before，循环查询最多 100 条，处理后这些记录离开当前查询，再读更早记录；二手则沿游标每页最多 40 条先收集全部 ID，再分批修改。写接口仍逐条校验归属和状态。这里的“全部”限定当前类别及身份，普通订单只处理已完成或已取消记录。

### Q82：每批 20 条，能保证一次“全部清理”全成功或全失败吗？

**答：** 不能。一个云函数写请求中的 1–20 条由同一事务提交，但 25 条会拆成 20+5 两个请求。第二批失败不会回滚第一批，页面应显示已确认完成的数量并刷新剩余列表。20 是项目选择的批大小，不是数据库事务上限。跨批全局原子、补偿和持久作业调度都没有实现，不能把多个独立请求包装成一个事务。

### Q83：为什么批量处理返回后还要核对 clearedIds？

**答：** SDK 调用成功不等于业务完成全部目标。clearBatches 要确认回执是数组，且包含这批全部 ID，之后才更新进度和移出本地列表。clearedIds 也用于归档回执，不表示物理删除。若云端提交后响应丢失，页面数量只是已确认数量，可能少于实际提交；应复用待确认请求编号并重新读取，而不是直接换编号假设没执行。

### Q84：snapshotAt 是严格的数据库快照吗？

**答：** 不是。跑腿和举报后续查询把 before 作为创建时间上界，主要避免操作开始后新建记录不断进入，但它不会冻结旧记录的状态或别人同时恢复的结果。二手游标也绑定筛选和用户作用域，回收站还会实时排除过期数据。严格快照需要额外机制；当前只是明确边界的分批查询，遇到重复 ID 或游标会中止提示，而不是无限循环。

### Q85：删除一个待处理举报后，管理员还能处理吗？

**答：** 可以。本人归档或清理只更新 reporter 相关字段，不改变举报 status、原因、目标摘要或管理审计，也不移除管理员队列中的业务记录。本人在保留期内恢复后仍按原举报查询处理结果。这个设计让“整理我的记录”和“是否继续治理”分开；否则用户一删历史就可能破坏管理依据。

### Q86：如何复用统一订单页，而不是复制三份页面逻辑？

**答：** createOrderCenter 返回 Page 配置，统一订单、兼容二手订单列表和独立回收站通过默认 kind 与 trashOnly 复用工厂；WXML、举报逻辑与操作样式也独立复用。kind 控制业务类型，role 控制身份筛选，status 控制业务状态，view 控制普通/回收站。发起操作前设置 busy 并递增 request，阻止旧读取覆盖结果及处理途中切换语境。共享前端不意味着把后台规则强行合成一套。

### Q87：回收站为什么既能左滑，又保留清理按钮？

**答：** 左滑提高熟悉用户的操作效率，可见按钮帮助第一次使用的人发现功能，也避免只有隐藏手势。组件先判断横向与纵向意图，普通上下滚动不应展开侧滑；父页管理展开行，并在滑动结束后短暂抑制点击，减少误入详情。最终清理仍经过确认和服务端校验。当前实现需后续窄屏与手势回归，不能仅凭源码说明就说体验已验收。

### Q88：商品卡片长短不齐，怎样修复才容易维护？

**答：** 先统一信息结构与占位空间：封面固定高度，标题限制两行且保留两行高度，标签、价格、区域和底部各有稳定区域；长内容省略后在详情查看。订单和举报按钮则共用 176rpx×84rpx 样式、红色描边危险动作及右侧对齐，时间另起一行。不能只缩小字号掩盖布局问题；这些是当前设计实现，最新版本尚无布局测试结论。

### Q89：近期功能实现了，但没有测试，简历和交接怎么写？

**答：** 明确说源码基线 4d45fa9 实现了统一页面、三类归档和批量清理；历史记录显示部署、索引回读和预览打包完成，但近期功能未回归。76 项通过属于 c4bc01e，二手三轮验收还保留手机取消收藏证据差异。文档核对、打包、部署 Active 和真实业务验收是不同证据，不把它们合并成“新版全部通过”。

### Q90：如果继续做回收站，你会优先补什么？

**答：** 先补权限、旧字段、到期边界、25 条跨批失败、响应丢失、并发恢复和切换页面的验证，再根据实际历史量评估持久批处理作业、断点进度及分页体验。还应审查旧幂等结果重放后的可见性，并单独制定共享凭证的保留与销毁策略。当前实现不包含这些全部能力；改进优先级由实际风险和使用量决定。
