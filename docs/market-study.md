# 校园二手模块：技术学习与面试补充

核对日期：2026-11-13。依据当前工作区代码；真实送检、回调和双账号验收情况见 [验收记录](acceptance.md)，不能用本地模拟证明微信平台已通过审核。

## 1. 从一张图到一件商品

```text
chooseMedia → getImageInfo → compressImage → 文件大小检查
→ media.upload：校验 base64、文件头、700KiB 上限
→ 事务保留 media_assets、当天上传额度
→ 私有存储上传 → 临时地址 → 微信 mediaCheckAsync
→ 保存 traceId → 等待真实 wxa_media_check
→ media-callback 校验平台来源、AppID、事件和版本
→ media_checks 按 trace 固定 ID 写入
→ media.status 查询 → 全部图片通过 → products.create
```

客户端依次尝试 1600/1200/900 像素长边与 75/55/35 质量，检查实际文件字节数，不以“压缩 API 成功”代替大小合规。后端不信任文件扩展名，校验 JPEG/PNG 文件头；客户端检查是交互优化，后端检查才是安全边界。

`media_assets` 保存所有者、对象引用、内容哈希、trace 与商品绑定；`media_checks` 独立保存平台审核结果。两张表的意义是允许回调先于上传事务到达：回调不必找到资产才能落库，查询状态时再通过 trace 关联。

审核 API 是外部副作用，不能和数据库组成同一事务。上传失败重试使用相同 operationId、对象路径和内容哈希；并发外部调用可能产生多个 trace，资产最终保留首个已提交 trace。不能宣称跨存储/审核/数据库实现“严格 exactly-once”。

回调从 SDK 上下文读取 SOURCE，不接受调用参数声称“我是平台”。只有 `wx_callback`、绑定 AppID、正确事件和版本才处理；按 trace 固定 ID 首条结果生效，重复回调不能把拒绝改为通过。35 分钟仍无结果视为 ERROR，需按受限重试流程处理；不允许手工跳过审核。

**阅读顺序：** [客户端压缩](../miniprogram/services/images.js) → [媒体业务](../cloudfunctions/campus-api/modules/media.js) → [存储与审核适配](../cloudfunctions/campus-api/lib/media.js) → [回调](../cloudfunctions/media-callback/handler.js)。

**练习：** 在本地测试中先送回调再保存资产；重复送相同事件；将拒绝结果后追加 pass；把来源改成 wx_client。分别说明预期状态与拒绝原因，禁止向真实库伪造通过结果。

## 2. 收藏计数为什么需要事务

只在前端切换星标不能防止重试或多设备竞争。当前收藏 ID 为用户和商品组合的哈希，记录保留 `active` 状态。设置为 true 时，只有旧状态不是 true 才加一；设置为 false 时，只有旧状态为 true 才减一。

收藏状态、商品 favoriteCount 和 rankKey 在同一事务更新；事务冲突重新读取旧值后再决定增减。用户自己的商品不可收藏；下架后仍允许移除收藏，但收藏列表不再返回被隐藏的正文和图片。

**读代码：** [products.js 的 favorites.set/list](../cloudfunctions/campus-api/modules/products.js)。**练习：** 相同用户同时提交 15 个收藏请求，验证只有一条有效收藏、计数为 1，再取消验证为 0。这个测试是本地并发模型，不是 15 个真实微信用户。

## 3. 服务端搜索、游标与动态列表

关键词统一小写，查询 title+description 组成的 searchText。先转义正则元字符，例如 `C++` 应匹配字面内容，`.*` 不能变成匹配所有商品的表达式。分类、在售状态和可见性始终由服务端共同过滤。

每次查询取 pageSize+1 条，额外一条用于判断是否有下一页；返回最后一条的排序键。排序键含时间/评分和唯一 ID，避免同时间记录没有确定顺序。游标带筛选签名、用户作用域和时间上界，切换筛选不能沿用旧游标。

游标用 Base64URL 编码，不是加密或授权凭据；服务端仍独立执行身份和业务过滤。`asOf` 只限制新创建记录，不冻结已有商品的评分或状态。收藏变化会移动推荐位置，前端合并分页时按 ID 去重，但仍可能漏看跨页移动的记录；刷新重查，不能承诺强一致快照分页。

**读代码：** [market.page/keyword/literal](../cloudfunctions/campus-api/lib/market.js)、[查询处理器](../cloudfunctions/campus-api/modules/products.js)、[商品列表](../miniprogram/pages/products/list/index.js)。

## 4. 可解释的推荐公式

```text
score = 72 × log2(1 + 收藏数) - (当前小时 - 发布时间小时)
      = 发布时间小时 + 72 × log2(1 + 收藏数) - 当前小时
```

同一次排序中，“当前小时”对所有商品相同，可以从排序键中去掉。因此存储 `发布时间小时 + 72 × log2(1 + 收藏数)` 即可，无需每小时更新全表；发布和收藏变化时重算。

从 0 到 1 次收藏加 72 分，相当于弥补 72 小时的发布时间差；从 1 到 3 次收藏也加 72 分。对数压低热门商品继续累积的边际优势，但 72 是产品参数，并非通过真实点击率实验训练出的权重。该方法没有用户画像，也没有协同过滤或机器学习。

**练习：** 建立相隔一天的两件商品；先验证新的排前，给旧商品增加一次收藏验证反超，取消收藏验证恢复。代码与用例位于 [rankKey](../cloudfunctions/campus-api/lib/market.js) 和 [market.test.js](../tests/integration/market.test.js)。

## 5. 单商品单预约与线下交付

商品与订单是两个实体。商品状态 `AVAILABLE/RESERVED/SOLD/WITHDRAWN` 表示能否再次预约；订单状态表示双方交易进度。预约事务内重读商品，要求在售且没有 activeOrderId，再同时创建订单、把商品设为 RESERVED。

订单保存标题、价格、公开区域和双方昵称快照；之后商品状态变化不改写既有交易证据。新预约直接进入 ACCEPTED（待当面交付），旧 PENDING 订单仍由卖家确认；买家验货及线下付款后确认完成。取消协商被拒绝进入 DISPUTED；管理员裁定必须留原因与审计。完成释放预订并设为 SOLD；取消则正常商品重新 AVAILABLE，被管理下架的商品保持 WITHDRAWN。

双方各自在 `product_orders` 上保留个人归档标记、归档时间与到期时间，不删共享交易和留言。普通订单列表排除本人的活动归档；回收站按本人到期时间过滤并使用归档排序键分页。到期后详情也拒绝该用户访问，避免从旧链接恢复过期记录。

状态推进与发送留言都会写双方用户版本，使封禁操作与新业务动作发生事务竞争。前端按钮只表达操作入口，接口仍必须检验角色和当前状态。这里没有扣款、退款、物流或支付回调，不能把“确认收货”解释为在线支付完成。

**读代码：** [product-orders.js](../cloudfunctions/campus-api/modules/product-orders.js)、[market-admin.js](../cloudfunctions/campus-api/modules/market-admin.js)。

## 6. UI 与验证方法

ColorUI 官方文件保留固定提交和许可证；页面级导入主样式，项目覆盖样式放在自身目录。微信原生 button 的默认宽度可能压过组件预期，实际模拟器发现分类按钮 184px 后，通过作用域选择器修正。不能仅以编译通过判断布局正确。

管理台真实接口读取和长内容排版检查分开：前者使用测试环境管理员，后者仅替换浏览器内存中的接口返回，不向云端制造商品。检查 1280/390/320px 的横向尺寸，并看截图核对标签、按钮与文本是否可读；没有横向滚动也可能存在竖排标签等缺陷。

## 面试补充：Q61–Q73

### Q61：NoSQL 是不是没有数据库？数据如何持续保存？

**答：** 有数据库。这里用 CloudBase 文档数据库保存 JSON 形态的业务文档，并使用云存储保存图片。NoSQL 表示不是通过关系表和 SQL 作为当前访问模型，不表示没有持久化。云函数实例退出后数据仍在云端；本地 MemoryStore 只是测试替身。

### Q62：为什么图片上传成功后还不能发布？

**答：** 上传成功只表示字节入库，审核是另一条异步流程。只有可信回调记录 PASSED、所有图片属于发布者且未被其他商品绑定，商品创建事务才通过。未审核、review、risky、超时和接口异常都不能视为通过。

### Q63：为什么要两个云函数？

**答：** campus-api 面向经身份校验的业务调用，media-callback 面向微信平台事件。两者入口和信任来源不同，所以回调单独部署；不是为了堆微服务数量。两者共享文档数据库，业务写操作仍尽量保持一个事务。

### Q64：怎么处理回调重复、乱序或提前到达？

**答：** 回调结果按 trace 哈希独立落库，不依赖资产已经提交。首次结果生效，重复结果无操作；后续矛盾结果不能升级为通过。上传事务保存 trace 后可关联早到结果。未知 trace 最终没有资产引用，也不能直接让某个商品发布。

### Q65：如何证明收藏不会重复增加？

**答：** 用户/商品组合固定 ID 防止多条逻辑收藏，事务检查 active 是否真正改变，再增减商品计数和推荐键；请求级幂等负责重复网络请求。测试要同时覆盖同请求重试与不同请求编号的并发，而不只验证单击按钮。

### Q66：你的推荐为什么不需要定时刷新分数？

**答：** 展开公式后，当前时间对所有商品是同一常数，不改变排序，所以排序键只存发布时间小时与收藏对数分。收藏变更时重算即可。它是规则排序，不是针对每个用户训练的个性化模型。

### Q67：游标分页是不是绝对不会漏数据？

**答：** 不是。时间/ID 键和筛选绑定改善稳定性，创建时间上界阻止新记录挤进本次翻页；但热度和可见性会变化，已有商品可能跨页移动。前端去重解决重复显示，刷新解决重新发现；需要严格快照就要另行设计版本或快照集合。

### Q68：为什么图片设私有，但列表仍能显示？

**答：** 列表只请求商品 ID，云函数检查可见性和图片审核后签发短期 URL。客户端不能提交任意对象路径要求签名。私有存储不等于签出的链接不可分享；已发出链接可能在有效期内继续访问，下架只停止后续签发。

### Q69：怎样防止两人同时购买同一件商品？

**答：** 在事务中检查商品 AVAILABLE 和 activeOrderId 为空，写商品预订与订单。并发事务竞争同一商品，失败方重读后看到 RESERVED 而被拒绝。小程序的同步锁减少连点，但数据库事务才约束多个客户端。

### Q70：部署显示 Active 为什么还可能不能上传图片？

**答：** Active 只代表函数可运行。存储、微信云调用权限、送检 API、消息推送、回调来源和数据库规则是不同环节。本项目曾遇到 -604101，后来通过开发者工具增量上传 `config.json` 同步权限。真实回调上下文使用 `wx_callback`，源码若校验成其他来源，即使平台已经返回 pass，也不会生成正式结果；需要以新的真实送检、回调落库和状态查询验证闭环。

### Q71：为什么“删除记录”没有直接删除订单文档？

**答：** 订单是买卖双方共享的交易凭证。个人整理列表只改变自己的归档标记与期限，另一方和管理员仍需读取原记录。物理删除会破坏对方历史和争议证据。这里用服务端身份选择 buyer/seller 字段，只有已完成或已取消订单可以归档。

### Q72：回收站过期怎样避免记录又出现在普通列表？

**答：** 普通列表一直排除本人的归档标记，回收站额外检查服务端到期时间。到期只停止展示和恢复，不自动清除归档标记。恢复动作必须在到期前走事务并只清除本人的字段；重试归档不会延长保留期。

### Q73：评论响应慢，为什么不直接取消内容审核？

**答：** 审核是发布条件，不能靠绕过它换速度。先测量端到端耗时、云函数、数据库与审核耗时；本轮删除的是评论成功后的整帖重读，直接用保存回执更新评论与数量，并用请求序号阻止旧列表覆盖新评论。订单详情则把订单与首批留言合并为一次云函数请求。
